## ch 이메일.
발신하는 메시지:User 에이전트 내부의 queue에 쌓이고.
수신된 메시지:user mail box에 쌓인다.
메일 박스에는 수신된 메시지가 들어있고
발신 큐에는 전송 대기중인 메시지가 순서대로 쌓여있음
서버간 SMTP 프로토콜을 이용하여 메일을 전송.
클라이언트:메일을 보내는 발신 메일서버
서버:메일을 받는(수신) 메일 서버.
메일 서버는 유저 메일박스,발신용 큐를 관리한다.
서버간 통신은 모두 smtp를 통해 이루어진다.

RFC.
smtp(연결 지향 tcp 방식)
직접 전송:핸드셰이킹->메시지 전송->연결 종료. http 유사.
명령/응답 교환 방식: 명령은 아스키 텍스트. 응답은 상태코드와 구문.
메일 데이터는 7비트 아스키만 허용.
****
SMTP Simple mail transfer protocol.:지속적 연결을 사용한다.
헤더와 본문을 7비트 아스키로만,
http:pull(클라이언트가 요청시 응답.)
SMTP:push(발신 서버가 즉시 전송)
둘다 아스키 기반 명령/응답.상태코드 쓰긴함
http:객체마다 각각 별도 응답 메세지 캡슐화.
smtp:여러 개 객체를 하나의 메일 메시지로 전송.
메시지 경계: HTTP는 메시지별 경계가 명확, SMTP는 CRLF.CRLF로 본문 끝을 표시

Domain name system.
분산 계층형 데이터 베이스. 도메인을 ip로 ip를 도메인으로 변환. 어플리케이션 계층에서 동작하지만,네트워크 전반에 필수.
nslookup www.google.com → DNS 서버에 질의 → IP 주소(예: 172.217.15.4) 반환
****
DNS 서비스.
중앙화된 DNS는 단일 장애점,트래픽 집중,유지 보스 문제가 발생한다.
DNS 서비스는 이름->주소 변환 외에도 별칭 부하 분산 기능 담당.
www.amazon.com은 여러 물리 서버(IP)를 가지며, DNS가 라운드로빈(Round Robin)으로 배분
****
DNS: a distributed, hierarchical database
DNS 계층 구조: 루트 → TLD(.com 등) → 권한 있는(Authoritative) 서버

클라이언트는 계층을 단계별로 질의(Iterative Query)하며 IP를 해석
.(루트) → .com 서버

.com → amazon.com 서버

amazon.com 서버 → www.amazon.com = 176.32.103.205
****
ROOT NAME Servers:DNS 계층의 최상위로 어떤 TLD도 모를때 마지막으로 참조하는 서버입니다.예시).xyz 같은거.
DNSSEC로 위 변조를 방지하며,ICANN이 관리를 총괄합니다.
****
TLD:Top Level Domain 최상위 도메인 서버.
.com .org 국가별 최상위 도메인 등을 관리.
**권한 있는 DNS 서버(Authoritative DNS)**는 특정 도메인에 대한 최종 IP 매핑 정보를 갖고 있습니다.
example.com의 IP를 묻는다면, .com TLD 서버가 example.com 권한 서버 주소를 알려주고, 해당 권한 서버가 실제 IP를 반환합니다.
****
Local DNS:엄밀히 속하지 않은 서버.
각ISP는 하나이상의 로컬 dns 서버를 운영.
Default name Server라고도한다.
로컬 DNS 서버는 사용자 가까이에 위치해, 응답 속도를 높이고 상위 서버의 부하를 줄여 줍니다.
로컬 캐시(TTL 기반)로 반복 질의 시 응답 시간을 단축하지만, 정보 신선도가 떨어질 수 있습니다.
****
iterated query:반복 질의.
예시: engineering.nyu.edu 호스트가 gaia.cs.umass.edu의 IP 주소를 알고 싶을 때
서버가 “내가 이 이름은 모른다. 대신 이 서버에 물어봐라”라고 응답
로컬 DNS가 상위 서버에 질의할 때,
한 단계씩 알아온 권한 서버 정보를 받아 다시 요청을 이어가는 방식입니다.
클라이언트는 상위 서버에 여러 번 질의하지만,
각 응답마다 “다음 돌릴 서버” 정보만 받습니다.
로컬 DNS → 루트 서버 → “.edu 서버에 물어보세요”
로컬 DNS → .edu 서버 → “cs.umass.edu 서버에 물어보세요”
로컬 DNS → cs.umass.edu 서버 → IP 반환
****
재귀 질의:recursive query
클라이언트가 로컬 DNS에 한 번만 질의하면,
로컬 DNS가 루트→TLD→권한 서버를 차례로 반복 질의하여 최종 IP를 반환합니다.
로컬 DNS가 재귀적으로 상위 서버에 요청을 중계하므로,
클라이언트는 한 번만 질의하면 됩니다.
계층 상위 서버의 부하가 커질 수 있습니다
****
DNS Caching.
일단 이름 서버(Name Server)가 이름↔주소 매핑을 알게 되면, 그 매핑을 **캐시(Cache)**에 저장한다
캐시 항목은 일정 시간이 지나면 **만료(TTL, Time To Live)**되어 사라진다
TLD 서버 정보는 보통 로컬 네임 서버(Local DNS)에 캐시되므로
→ 루트 네임서버(Root DNS Servers)는 자주 방문할 필요가 없다
매핑 정보 갱신을 위한 IETF 표준(RFC 2136)이 제안되어 있음.
DNS 캐싱으로 반복된 질의를 방지, 응답 속도를 높이고 상위 서버 부하를 줄인다.
하지만 TTL이 지나야 갱신되므로, IP 변경 시 전파 지연이 발생할 수 있다.
****
DNS records
DNS:distributed database storing resource records (RR) 분산 데이터 베이스로 리소스 레코드를 저장한다.
형식:RR format: (name, value, type, ttl)	
RR(Resource Record) 하나가 도메인별 서비스 정보를 담고,
NS/A/CNAME/MX 등 종류에 따라 역할이 달라진다.
NS 레코드: Name=도메인(예: foo.com), Value=권한 서버 호스트명(Authoritative Name Server)
A 레코드: Name=호스트명(예: www.foo.com), Value=IPv4 주소
CNAME 레코드: Name=별칭(Alias, 예: www.ibm.com), Value=정식명(예: servereast.backup2.ibm.com)
MX 레코드: Value=해당 도메인의 메일 서버 호스트명(예: mail.foo.com)
****
DNS 프로토콜 메세지.
DNS 질의(Query)와 응답(Reply) 메시지는 동일한 형식을 가진다:
 -식별자(Identification): 질의 시 16비트 숫자, 응답은 동일한 번호 사용
 -플래그(Flags): 질의/응답 구분, 재귀 요청 허용 여부, 재귀 지원 여부, 권한 응답 여부
 Identification과 Flags로 메시지 종류·요청 범위를 표시하고,
이어서 네 개의 섹션 헤더가 각 레코드 수를 명시한다.
****
슬라이드 19: DNS protocol messages (2)
Questions에 요청 세부를(name,type.), Answers에 실제 RR집합 매핑을, Authority에 권한 서버 목록을,
Additional에 추가 정보를 담아 확장성 있게 설계됨. 
****
도메인 등록 시 Registrar→TLD 서버에 RR을 추가하고,
개별 호스트(MX, A 등)는 자체 권한 서버에 정의한다.
신규 도메인 alice-co.com을 등록하면,
Registrar가 .com TLD에 NS/A 레코드를 넣고,
회사 내부 DNS에서 mail.alice-co.com MX 레코드를 관리합니다.
****
Dns Security.
DNS의 분산 구조를 노려, 루트·TLD 서버를 과부화시키거나 스푸핑·중간자 공격을 통해 잘못된 정보를 퍼뜨릴 수 있습니다.
로컬 DNS 캐싱, 트래픽 필터링, DNSSEC 등이 방어 수단이 됩니다.

도스 어택.

- 현재까지는 성공 사례 없음
-트래픽 필터링으로 방어
-로컬 DNS가 TLD 서버 IP를 캐시해 루트 서버 우회 가능 ​
-최상위 도메인(TLD) 서버 공격,더위험함.

리다이렉트 공격
-중간자 공격(Man-in-the-middle): DNS 질의를 가로챔 ​
- DNS 캐시 중독(Poisoning): DNS 서버에 가짜 응답을 보내 캐시시킴
DNS를 DDoS에 악용하기
-발신지 주소 위조 스푸핑 후 대상 IP로 대량 질의 전송 → 증폭 효과 이용.
공격자가 사용자 IP를 스푸핑해 “example.com”을 조회 → DNS 서버가 증폭시켜 대량의 응답을 대상 서버로 발송하며 가용성을 저하시킴.
****
P2P 아키텍처 (Peer-to-peer Architecture)
-항상 켜져 있는 서버 없음
-임의의 단말(피어) 간 직접 통신
 피어 간 요청(Request)·제공(Service)이 상호 교환됨 ​
-자체 확장성(Self-Scalability): 새로운 피어는 용량과 수요를 동시에 제공
중앙 서버 없이 단말 간 직접 데이터 교환 → 네트워크 부하 분산 및 확장성 확보
반면, 피어의 가변성(연결·IP)으로 관리·보안이 복잡해집니다.
****
서버 파라미터 정리.
F: 파일 크기

uₛ: 서버 업로드 대역폭

uᵢ, dᵢ: 각 피어 i의 업로드/다운로드 대역폭

dₘᵢₙ: 최저 피어 다운로드 속도
****
Client-Server 분배 시간
▪ 서버 전송: N개의 파일을 순차적으로 업로드해야 함:
• 하나 전송 시간: F/uₛ
• N개 전송 시간: N F/uₛ
▪ 클라이언트 다운로드:
• 최소 F/dₘᵢₙ
Dc-s>=max{NF/us,F/dmin}.
****
P2P 분배 시간:
▪ 서버: 최소 한 번 복사본 업로드 → F/uₛ
▪ 클라이언트: 각자 다운로드 → F/dₘᵢₙ
▪ 전체 피어는 NF bits 다운로드 필요, 최대 업로드 용량 uₛ + Σ uᵢ
DP2P>max(F/uₛ F/dₘᵢₙ NF bits/uₛ + Σ uᵢ)
서버 부담 감소: 서버는 최소 한 번만 업로드
스케일링: 피어들의 업로드 용량이 모여 전체 분배 속도를 높임

이해를 돕는 예시
예시 매개변수: u=1 Mbps, F=3600 Mb (F/u=1 시간), us=10 Mbps, dₘᵢₙ≥10 Mbps

N=5일 때

클라이언트-서버: 5×3600 Mb/10 Mbps = 1800 초 = 0.5 시간

P2P: max{360 초, 360 초, 5×3600 Mb/(10+5×1 Mbps)=300 초} = 360 초 (0.1 시간) → 훨씬 빠름

N이 20일 때

클라이언트-서버: 20×3600/10 = 7200 초 = 2 시간

P2P: max{360 초, 360 초, 20×3600/(10+20×1)=240 초} = 360 초 (0.1 시간)
