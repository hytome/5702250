## transport layer 서비스 원리 이해.
UDP:user datagram protocol.
-connectionless transport:비연결성 전송.
TCP:Transmisson control protocol.
-connection-oriented reliable trasport:연결 지향 신뢰성 전송.
-congestion control-혼잡제어.
다중화/역다중화:

다중화(multiplexing): 여러 프로세스에서 나온 데이터를 하나의 전송 채널로 합치는 것

역다중화(demultiplexing): 수신 측에서 어떤 프로세스로 전달할지 분리하는 것

예시: 하나의 서버에 여러 채팅 클라이언트가 접속했을 때, 포트 번호로 구분하여 메시지를 올바른 클라이언트로 전달

신뢰성 있는 데이터 전송: 손실·오류 패킷을 검출하고 재전송하여 완전한 데이터 전달 보장

흐름 제어: 송신 속도를 조절해 수신 버퍼 오버플로우 방지

혼잡 제어: 네트워크가 과부하될 때 송신 속도를 줄여 전체 네트워크 성능 유지
****
UDP vs. TCP:

UDP(User Datagram Protocol): 간단한 헤더, 손실·순서 보장 안 함. DNS, 스트리밍 등에 사용

TCP(Transmission Control Protocol): 연결 설정, 순서 보장, 오류 제어, 흐름·혼잡 제어 포함. 웹(HTTP), 이메일(SMTP) 등에 사용
****
논리적 통신(logical communication): 애플리케이션 관점에서 직접 연결된 것처럼 데이터 전송을 추상화.
세그먼트(segment): 전송 계층 단위 데이터 단편

예시:

웹 브라우저→서버 요청: 브라우저가 HTTP 요청 메시지를 TCP 세그먼트로 분할하여 전송

서버→클라이언트 응답: TCP가 세그먼트를 재조립하여 최종 메시지로 복원
****
트랜스 포트와 네트워크 레이어 서로 비교 예시
비유의 핵심:

네트워크 계층은 집 대 집 간 우편 배달(“postal service”)을 담당

전송 계층은 집 안에서 올바른 아이에게 편지를 전달하고, 보낼 편지를 봉투별로 모아 우편부에게 전달
네트워크는 논리적 hots 통신.
트랜스 포트는 논리적 프로세스 통신. 
****
transport Layer actions.
IP: Internet Protocol

segment: Transport-layer segment

설명 및 예시

송신 측은 애플리케이션이 요청한 데이터를 작은 단위(세그먼트)로 쪼개고, 목적지·순서 정보 등을 헤더에 담아 IP 계층으로 넘깁니다.

예시: 웹 브라우저가 “GET /index.html” 요청을 TCP 세그먼트로 나누어 전송

수신 측은 IP에서 전달된 세그먼트를 받아 헤더 검사를 통해 오류나 순서 여부를 확인하고, 다시 원본 메시지로 조립하여 애플리케이션에 전달합니다.

예시: 서버가 받은 TCP 세그먼트를 재조립해 HTTP 응답 메시지로 복원
****
Tcp:순서보장전송
Udp:순서 미보장 전송
제공되지 않는 서비스:지연 보장,대역폭 보장.
TCP는 3-way 핸드셰이크로 연결을 설정하고, 오류 복구·재전송·순서 제어·흐름·혼잡 제어를 포함해 안정적인 통신을 보장합니다.

예시: 웹 페이지 요청·응답(HTTP/HTTPS), 이메일 송수신(SMTP/IMAP)

UDP는 헤더가 작고, 연결 설정 과정이 없어 오버헤드가 적지만 전송 중 손실·순서 변경이 발생할 수 있습니다.

예시: 실시간 스트리밍, DNS 질의, VoIP(Voice over IP)
****
Multiplexing,Demultiplexing.
다중화(Multiplexing): 하나의 호스트에서 여러 애플리케이션(소켓) 데이터를 모아 전송

예시: P2P 프로그램이 동시에 여러 피어에게 데이터를 보낼 때, 각 연결별로 포트 번호를 헤더에 붙여 구분

역다중화(Demultiplexing): 목적지 호스트가 도착한 세그먼트의 헤더(port/IP)를 보고 어느 애플리케이션으로 전달할지 결정

예시: DNS 클라이언트가 보낸 쿼리와 웹 브라우저가 보낸 요청을 같은 IP라 하더라도 포트 번호로 구분
****
역다중화 작동 방식.
호스트는 IP 데이터그램(datagram)을 수신  
   • 각 데이터그램에 출발지·목적지 IP 주소 포함  
   • 하나의 데이터그램이 하나의 전송 계층 세그먼트를 운반  
   • 세그먼트마다 출발지·목적지 포트 번호 포함  
   호스트는 IP 주소와 포트 번호를 사용해 세그먼트를 올바른 소켓(socket)으로 전달  
  IP 계층이 받은 패킷 속의 헤더(IP 주소, 포트 번호)를 보고 전송 계층으로 넘기면,

전송 계층은 다시 포트 번호를 보고 대상 애플리케이션 소켓으로 전달합니다.

예시: 클라이언트 A(포트 5000)와 B(포트 5001)가 동시에 DNS 서버(포트 53)에 질의할 때,
응답이 돌아오면 클라이언트 포트 번호로 구분해 각각의 소켓으로 배달 
****
비연결성 역 다중화. udp.
UDP는 연결 설정 과정이 없어, 포트 번호만 보고 소켓을 선택합니다.

예시: 두 개의 서로 다른 클라이언트(포트 5000, 5001)가 같은 서버 포트 6428로 보낸 패킷은 모두 같은 DatagramSocket(6428)이 받음.

이 특징 때문에, 서버 측에서는 메시지 발신자를 IP·포트 쌍으로 구분해 직접 응답해야 합니다.
****
connection-orientd 역다중화.
TCP: Transmission Control Protocol

4-tuple: Four-tuple (source IP, source port, destination IP, destination port) 출발지,목적지.

설명 및 예시

TCP는 연결(connection)마다 상태(state)를 유지하므로, 단순 포트 번호뿐 아니라 4-튜플 정보를 이용해 들어오는 세그먼트를 올바른 연결로 매핑합니다.

예시: 웹 서버가 동시에 여러 브라우저 세션을 처리할 때, 각 클라이언트의 IP/포트 조합이 달라서 서로 다른 TCP 소켓으로 구분됩니다.
호스트 A:9157 → 호스트 B:80  
호스트 C:9157 → 호스트 B:80  
호스트 B:80   → 호스트 A:9157

세 개의 세그먼트가 모두 IP B의 포트 80을 목적지로 하지만,  
출발지 IP와 포트가 달라 서로 다른 소켓으로 분배됩니다.
****
정리.
다중화/역다중화: 세그먼트 또는 데이터그램 헤더 필드 값에 기반  
UDP: 목적지 포트 번호만으로 역다중화  
TCP: 출발지·목적지 IP 및 포트(4-튜플)로 역다중화  
다중화/역다중화는 모든 계층에서 이루어짐
****
UDP는 헤더가 작고 상태 유지 오버헤드가 없어 실시간성(VoIP, 온라인 게임)이나 손실이 허용되는 멀티미디어 스트리밍에 적합합니다.

예시: 화상회의 애플리케이션은 약간의 패킷 손실을 감수하면서도 낮은 지연(latency)이 중요하기 때문에 UDP를 사용합니다.
****
UDP 세그먼트 헤더.
UDP 헤더는 출발지(source) 포트, 목적지(destination) 포트 두 개의 16비트 필드로 구성됩니다.

헤더 다음에는 애플리케이션이 보낸 실제 데이터(페이로드)가 위치합니다.

예시: DNS 쿼리는 애플리케이션 데이터를 페이로드로 포함하고, 출발지 포트(임의 할당), 목적지 포트 53을 헤더에 담아 전송합니다.
****
UDP-체크섬.
length 필드는 헤더 + 페이로드를 합친 전체 세그먼트 크기를 바이트 단위로 나타냅니다.

checksum 필드는 오류 검출을 위해 세그먼트 전체(헤더 및 데이터, IP 주소 포함)를 16비트 워드 단위로 합산한 1의 보수 결과입니다.

예시: 간단한 8바이트 데이터그램의 길이 필드는 8, 체크섬 필드는 계산된 무결성 값이 됩니다.
송신자는 세그먼트(‘5’와 ‘6’)의 16비트 워드 합을 계산해 체크섬에 담아 보냅니다.

수신자는 받은 데이터의 합을 다시 계산해 체크섬 필드와 비교합니다.

예시: 5+6=11, 전송·수신 시 값이 일치하면 오류 없음, 다르면 손상으로 간주합니다.
****
인터넷 체크섬은 1의 보수 합방식.
문제점:
1의 보수 합 방식은 서로 보완되는 오류(예: +k와 –k)가 발생하면 검출하지 못합니다.

예시: 두 워드 값이 각각 0x1234→0x1235, 0x5678→0x5677로 변화해도 합은 동일하여 오류를 간과할 수 있습니다.

시험 대비 포인트: 오차 검출 능력이 제한적이므로 TCP에서는 선택적 재전송·더 강력한 해시 등을 추가로 사용합니다.
****
Reliable Data Transfer—서비스 추상화
신뢰성 서비스 추상화는 애플리케이션이 “완전하고 순서 보장된(end-to-end)” 전송 결과만 보고, 중간 네트워크의 손실·오류·순서 변형을 신경 쓰지 않도록 해 줍니다.

예시: 파일 전송 애플리케이션이 중간에 패킷 손실이 있더라도, 전송 완료 시점에는 손상 없는 원본 파일을 받도록 보장.

실제 구현에서는 전송 계층이 불안정 채널(패킷 손실·파손·순서 
변경 발생) 위에 신뢰성 서비스를 만들어야 합니다.

송신 측(sender-side)은 재전송, 타이머, ACK 관리 등을 담당하고, 수신 측(receiver-side)은 오류 검출, 중복 제거, 순서 재조립 등을 수행합니다.
****
복잡도.
채널이 오직 손실만 발생한다면 단순 ACK+타임아웃(retransmission timeout)으로도 구현 가능(rdt2.1).

채널이 손실+손상을 다룬다면 체크섬·NACK 또는 연속 ACK 기법이 필요(rdt3.0).

채널이 손실+손상+순서 변경까지 발생한다면 슬라이딩 윈도우, 순서 번호(sequence number) 등으로 더 복잡해집니다(Go-Back-N, Selective Repeat).
****
rdt: Reliable Data Transfer protocol
udt: Unreliable Data Transfer function
udt_send(): rdt가 불안정 채널로 패킷 전송 시 호출  
rdt_rcv(): 채널에서 패킷 도착 시 호출  
deliver_data(): rdt가 상위 계층(애플리케이션)으로 데이터 전달 시 호출
