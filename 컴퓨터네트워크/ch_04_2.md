## 신뢰성 있는 데이터 전송.
rdt: Reliable Data Transfer protocol
FSM: Finite State Machine
단계적 개발: 먼저 이상적인 채널에서 rdt1.0, 그다음 오류 채널에서 rdt2.0~2.2 등으로 기능을 확장

단방향 전송: 실제 구현에서는 송신→수신만 모델링하지만, ACK·NAK 같은 제어 메시지는 반대 방향으로도 흐름

유한 상태 기계(FSM): 각 상태(state)에서 가능한 이벤트(event)에 따라 다음 상태와 동작(actions)이 결정되는 설계 기법

예시: 채팅 앱에서 “메시지 전송 대기”·“ACK 대기” 같은 상태로 나누어 설계
****
make_pkt: Make Packet function

udt_send: Unreliable Data Transfer send function

deliver_data: Deliver Data function

설명 및 예시

이상적인 채널: 네트워크에서 비트 노이즈나 손실이 전혀 없다고 가정

rdt1.0 구조: 송신자는 단순히 애플리케이션 데이터를 패킷으로 만들어 보내고, 수신자는 그대로 되돌려 애플리케이션에 전달

예시: 로컬 프로세스 간 파이프(pipe) 통신처럼 손실 없는 채널에서 동작
****
rdt2.0 비트 오류가 있는 채널
비트 오류: 전송 중 잡음(noise)으로 일부 비트가 반전될 수 있음

체크섬: 수신 측에서 받은 패킷 전체에 대해 다시 계산한 체크섬과 송신 측이 보낸 값 비교

예시: 전화 통화 중 “잘 들렸어?”라고 다시 확인하는 것처럼, 데이터 전송에서도 오류 확인 후 재전송이 필요
****
rdt2.0 – ACK/NAK 기반 복구
ACK: Acknowledgement

NAK: Negative Acknowledgement

설명 및 예시

ACK/NAK: 사람 간 대화에서 “응, 잘 들려”(ACK) 또는 “다시 말해 줄래?”(NAK)와 유사한 기법

stop-and-wait: 매 전송마다 응답이 올 때까지 대기하므로 간단하지만 효율은 낮음

예시: 메신저 읽음 확인(Read Receipt) 기능처럼, 수신 확인 후 다음 메시지 전송
****
rdt2.0 – FSM 명세 (Sender & Receiver)
FSM: Finite State Machine

rdt_send / rdt_rcv: Reliable Data Transfer send/receive functions

udt_send: Unreliable Data Transfer send function

설명 및 예시

송신자 FSM: 패킷 전송→응답 대기→재전송 또는 다음 전송 단계로 전이

수신자 FSM: 항상 “수신 대기” 상태, 손상 시 NAK, 정상 시 데이터 전달과 ACK 반복

예시: 우편물 배달 확인 시스템에서 “발송 대기→배달 확인→재배달 요청 또는 완료” 흐름과 동일
****
 FSM 명세 계속 & 프로토콜 필요성
 문제점: 송신자(sender)는 패킷이 제대로 도착했는지, 또는 손상됐는지 자체적으로 알 수 없으므로, 수신자(receiver)가 명시적으로 피드백(ACK/NAK)을 보내야 합니다.

예시: 이메일을 보냈을 때 “읽음” 표시가 없으면 보낸 사람이 메일이 제대로 전달됐는지 확신할 수 없는 것과 같습니다.
****
rdt2.0: 오류 없는 동작
stop-and-wait 방식: 각 패킷 전송 후 반드시 ACK을 기다려야 함.

예시: 우체국에서 택배를 보낸 뒤, “배송 완료” 문자가 와야 다음 물건을 보낼 수 있는 절차와 유사합니다.
****
rdt2.0 – 손상된 패킷 시나리오 (Corrupted Packet Scenario)
손상된 패킷이 들어오면 수신자는 데이터를 버리고 NAK으로 재전송을 요청합니다.

예시: 전화 통화 중 소리가 깨지면 “다시 한 번 말씀해 주세요”라고 요청하는 것과 같습니다.
****
rdt2.0의 치명적 결함 (Fatal Flaw)
문제: ACK 또는 NAK마저 손상되면 송신자는 “재전송해야 하나?” “정상 수신된 건가?”를 판단할 수 없습니다.

해결: 패킷마다 고유 번호를 붙이고, 수신자는 이미 받은 번호의 패킷은 무시하도록 설계합니다.

예시: 택배 송장 번호를 도입해 “송장 1234”가 이미 도착했으면 같은 번호의 택배는 받지 않는 방식과 유사합니다.
****
rdt2.1 – 시퀀스 번호를 추가한 Sender FSM
- 패킷에 0 또는 1의 순서 번호(seq #) 추가
seq #: Sequence Number

설명 및 예시

두 개의 번호(0,1)만으로도 중복 처리 가능하며 FSM 상태가 두 배로 늘어납니다.

예시: 지그재그(Zig–Zag) 신호등처럼 0→1→0 순으로 번갈아 가며 패킷 식별 및 처리.
****
rdt2.1 – 수신자(Receiver) FSM
ACK: Acknowledgement

NAK: Negative Acknowledgement

seq #: Sequence Number

설명 및 예시

중복 방지·순서 보장을 위해 0과 1 두 가지 seq 번호만 사용합니다.

수신자는 항상 “현재 기대하는 번호”와 일치하는 패킷만 전달하고, 나머지는 NAK으로 재요청합니다.

예시: 택배 추적 시스템에서 “송장 번호 1001”만 받도록 설계하고, 다른 번호나 형식이 잘못되면 “재요청” 표시를 보내는 것과 유사합니다.
****
송신자 FSM이 두 배로 늘어난 이유는 “다음에 기대하는 seq 번호”를 상태로 기억해야 하기 때문입니다.

수신자는 이미 처리한 seq 번호의 중복 수신을 버림으로써 중복 전달을 방지합니다.

이 구조는 나중에 TCP의 NAK-free(NAK 없이 ACK만으로 처리) 설계로 발전합니다
****
rdt2.2 – NAK-free 프로토콜
rdt2.2: NAK 없이 동작하는 프로토콜

 rdt2.1과 기능 동일하되 ACK만 사용  
 NAK 대신 “마지막으로 정상 수신된 패킷”의 seq 번호를 포함한 ACK 전송  
 송신자는 중복된 ACK(이전 seq 재요청) 시 현재 패킷 재전송

→ TCP도 이 방식을 채택해 NAK 없이 구현
NAK이 사라지고, “마지막 수신한 seq 번호”를 ACK에 담아 송신자에게 알리면, 손상되거나 누락된 패킷을 재전송할 수 있습니다.

예시: 메시지 앱에서 “마지막으로 본 메시지 ID”를 계속 알려주면, 누락 메시지를 다시 보내도록 하는 기법과 유사합니다.
