## ch_06.md tcp 흐름제어.
네트워크가 보낸 데이터를 애플리케이션이 제때 읽지 못하면 수신 버퍼에 쌓이고, 결국 오버플로우 위험이 생깁니다.

예시: 동영상 스트리밍 시 플레이어가 디코딩을 못 따라가면 재생 버퍼가 가득 차 일시정지가 발생하는 것과 유사합니다.'
****
TCP는 rwnd 필드로 “지금 수신자가 얼마만큼의 여유 공간을 갖고 있는지”를 송신자에게 알려,

송신자는 이 값 이상으로 in-flight 데이터를 보내지 않습니다.

예시: 택배 보관함에 빈 칸이 5칸 남았다고 알려주면, 택배 기사가 그 이상은 담지 않는 원리와 같습니다.
****
rwnd 필드를 통해 동적으로 수신 여유 공간을 광고하므로, 송신자는 항상 최신 rwnd 값을 기반으로 전송량을 조절합니다.

예시: 비어 있는 주차 공간 수를 실시간으로 전광판에 표시해 진입 차량 수를 제어하는 시스템과 유사합니다.
****
Tcp 연결
데이터 교환 전에 송신자/수신자 간에 “핸드셰이크” 수행:  
핸드셰이크를 통해 양쪽이 연결 의사를 확인하고, 이후 사용할 초기 sequence number와 버퍼 크기를 동기화합니다.
전화 통화 전 “여보세요, 통화 괜찮나요?” → “네, 괜찮습니다” 확인 과정과 유사합니다.
****
2-way 핸드셰이크는 단순하지만, 실제 네트워크에서는 지연·손실·순서 변경이 발생해 실패할 수 있습니다.

TCP는 3-way 핸드셰이크로 보완하여, 클라이언트→서버→클라이언트 순으로 상호 확인을 수행합니다.

예시: 약속 장소에서 “거기 있어?” → “응, 여기 있어”만으로는 충분치 않아 “내가 곧 도착할게”를 추가로 주고받는 방식과 유사합니다.
****
혼잡 제어는 네트워크 전체의 과부하를 막기 위한 메커니즘이며, 흐름 제어는 송신자↔수신자 간 조절입니다.

예시: 고속도로 톨게이트가 막히면 전체 교통 정체(혼잡 제어 대상), 특정 차선에서 사고가 나면 해당 차선만 조절(흐름 제어)과 유사합니다.
****
혼잡 시나리오 1.
두 흐름이 동일한 라우터를 지나갈 때, 공유 대역폭 R을 반씩 나눠 각각 R/2를 얻습니다.

λ_in이 R/2에 가까워지면 지연이 급격히 증가하며, 이론상 더 이상 처리량이 늘지 않습니다.

예시: 두 대의 수도관에 물을 절반씩 분배하면, 각 파이프는 최대 절반씩만 흐를 수 있는 것과 같습니다.
****
혼잡 시나리오2.
하나의 라우터, 유한 버퍼
버퍼 용량이 한정되어 패킷이 손실되면 송신자가 재전송을 시도하면서, 네트워크로 들어오는 전체 트래픽 λ'_in이 원본 λ_in보다 커집니다.

이로 인해 더 큰 지연과 추가 손실이 발생해 혼잡이 악화됩니다.

예시: 주차장이 가득 차 차량이 되돌아갔다가 다시 진입을 시도할 때, 진입 시도로 인해 도로 정체가 더 심해지는 양상과 같습니다.
****
이상화 모델 – 완벽한 정보(Perfect Knowledge)
송신자가 라우터 버퍼 상태를 정확히 알고 있어, 버퍼가 꽉 찰 일이 없도록 제어하는 가상의 시나리오입니다.

예시: 주차 전광판에 빈 슬롯 수가 실시간으로 표시돼, 운전자가 빈 곳 있을 때만 진입하는 시스템을 상상해 보세요.
****
이상화 모델 – 일부 정보(Signaled Loss) some perfect knowledge
송신자는 드롭 이벤트를 정확히 인지해, 실제 손실된 패킷만 재전송하므로 불필요한 재전송이 없습니다.

예시: 택배가 분실된 경우에만 고객에게 자동 재배달 안내 메시지가 가는 시스템과 비슷합니다.
****
현실적 시나리오 – 불필요 재전송(Unneeded Duplicates)
실제 네트워크에서는 타임아웃 설정이 보수적일 수 있어, 이미 도착한 패킷인데도 재전송을 발생시켜 “용도에 맞지 않는” 중복 트래픽을 유발합니다.

예시: 택배가 정상 배달됐는데도 고객 문의 시스템 오류로 “배송 재확인” 알림이 또 가는 상황과 유사합니다.
****
AIMD  Additive Increase Multiplicative Decrease
가산 증가(Additive Increase): 혼잡이 없으면 천천히 윈도우 크기를 늘려 네트워크 대역폭을 탐색합니다.

곱셈 감소(Multiplicative Decrease): 혼잡(손실) 발생 시 윈도우를 절반으로 줄여 네트워크 부담을 완화합니다.

예시: 엘리베이터에 사람이 탈 때, 한 명씩 추가로 태우다가 갑자기 너무 붐비면 절반만 내리는 식으로 인원 조절하는 방식과 유사합니다.
처음에 1초에 10개정도 보내봄->성공->아 10개까지는 문제없이 잘가구나. 두번째 시도때 11개씩 보내봄.->이것도 성공.->또 성공할씨 또 하나씩 증가.->그러다 에러가 나는 순간이 옴 EX)30. 1.채널이 좋아도 최대 갯수 지정이 나서 에러. 2.아니면 그시점에 채널이 안좋아졌거나. ->아,30개는 못보내는구나. -> 그럼 반으로 줄여서 보내야지:15개 전송 ->다시 문제 없이 전송 댐.->다시 16개 전송 시작. 
****
TCP 송신자는 다음 조건을 만족할 때만 전송:
   LastByteSent − LastByteAcked < cwnd
TCP 전송률 ≈ cwnd/RTT (in‐flight 바이트 수)
송신자는 아직 ACK받지 않은 바이트 수가 cwnd를 초과하지 않도록 제한합니다.
네트워크 상태가 좋으면 cwnd를 늘리고, 혼잡 시 줄이며 자동으로 조절합니다.
****
TCP 슬로우 스타트 (Slow Start)
슬로우 스타트 단계에서는 빠르게 대역폭을 탐색하기 위해, 매 ACK마다 윈도우를 1 MSS씩 늘립니다.

결국 RTT당 윈도우가 두 배로 증가하는 지수 성장(exponential growth)을 보입니다.

예시: 소방호스의 물줄기를 서서히 세게 하다가 갑자기 빵 터트리는 듯 빠르게 늘리는 과정과 유사합니다.
****
TCP: 슬로우 스타트에서 혼잡 회피로 전환
질문: 지수 증가를 선형 증가로 전환하는 시점은?  
답: timeout 직전 cwnd의 절반에 도달했을 때.
ssthresh를 기준으로, cwnd < ssthresh일 때는 슬로우 스타트(지수 증가),
이후 cwnd ≥ ssthresh일 때는 혼잡 회피(선형 증가)로 전환합니다.
예시: 자전거 페달 초기에는 급가속으로 속도를 올리다가 일정 시점(속도 제한)에 도달하면 페이스를 유지하며 천천히 더 올리는 드라이빙과 유사합니다.
****
 병목 링크(“Bottleneck Link”)와 TCP
네트워크 전체가 아닌 **가장 좁은 지점(병목 링크)**의 상태가 TCP 성능을 결정합니다.

병목이 포화되면 추가 전송은 큐잉 지연과 손실만 늘리므로, 정확히 채우는 선에서 멈춰야 합니다.

예시: 수도관 중 가장 좁은 관 직경이 전체 수압을 결정하듯, 네트워크도 가장 느린 구간이 전체 처리량을 좌우합니다.
**병목 링크(bottleneck link)**란 네트워크 경로에서 가장 낮은 처리량을 가진 구간으로, 이 지점을 포화시켜야 end-to-end 처리량을 최대화할 수 있습니다.

예시: 수도관 중 가장 좁은 부분을 통해 전체 수압이 결정되는 것과 같습니다.
병목이 포화된 상태에서는 전송 속도를 더 높여도 end-to-end 처리량이 늘지 않습니다.  
– 그러나 포화 시 RTT(왕복 시간)는 늘어납니다.  
RTT 증가는 큐잉 지연이 커진다는 신호이므로, 네트워크가 꽉 찼음을 반영합니다.
****
TCP 공정성(Fairness) 목표
여러 연결이 자원을 공유할 때, 균등한 분배를 보장하는 것이 TCP의 중요한 설계 목표 중 하나입니다.

예시: 두 갈래 수도관이 하나의 원천에서 물을 나눠 쓸 때, 각각 절반씩 받는 구조와 같습니다.
**UDP 기반 애플리케이션**(멀티미디어 등)은 TCP 혼잡 제어에 구애받지 않고  
  – 일정한 전송률을 유지하며 손실을 감내  
  – 인터넷에 혼잡 제어를 강제하는 중앙 기관은 없음  
 **병렬 TCP 연결**  
  – 애플리케이션이 두 호스트 간 다수의 TCP 연결을 열어 대역폭을 나눠 쓸 수 있음  
  – 예: 대역폭 R인 링크에 이미 9개의 연결이 있을 때  
    • 새 앱이 TCP 1개 요청 → 처리량 R/10  
    • 새 앱이 TCP 11개 요청 → 처리량 약 R/2
